## git 历史澄清：旧方法是“清除”不是“目录占位符”

- 用户指出旧方法不是把 `.sqlite` 变成目录，而是**清除**。查 git 确认：
  - **v1.0 (`b9a8f62`, 2024-12) `unblacklist.py`**：真正的清除法。用 `SysContainerDomain-../../../../../../../../var/...` **路径穿越** + `ConcreteFile(..., contents=plistlib.dumps({}))` 把 `MobileIdentityData/{Rejections,AuthListBannedUpps,AuthListBannedCdHashes}.plist` 覆盖成空 `{}`；并把 **`/var/protected/trustd/private/ocspcache.sqlite3`(-shm/-wal) 写成 `contents=b''`** 即**截断 OCSP 缓存**。`reboot=False`。这是经典“清 OCSP 缓存”续命法。
  - **v2 (`555dba0`, 2026-04)**：改用 `Directory` 占位符（注释“using Directory now for persistence... messes up writes”），并**把 trustd 目标从 `ocspcache.sqlite3` 换成 `valid.sqlite3`**；域也从穿越改成 `DatabaseDomain`/`ProtectedDomain`。
  - **`844fccd`**：重命名为 `omega.py` 并加 iOS 27 三阶段保护备份。
- 关键研究结论：当前 omega.py 锁定 `valid.sqlite3`（权威库，iOS 27 自修复）可能是**回归**；旧的 `ocspcache.sqlite3` 是**缓存**，截断只强制重校验、给“临时窗口”，不一定被 `_SecFixTrustdFilePermissions` 自修复。且“清除”(ConcreteFile 空内容) 比“目录混淆”更确定，iOS 27 对后者直接 205。
- 待验证（符号级 diff 无法确认）：(1) `SysContainerDomain-../` 穿越在 iOS 27 是否仍可用；(2) `ocspcache.sqlite3` 在 iOS 27 的路径是否仍是 `/var/protected/trustd/private/`；(3) `flags=4` 拒绝是否仍挡 ProtectedDomain 写入。
- 建议下一步：实现诊断变体——用 `ConcreteFile` 空内容写入 `ProtectedDomain/trustd/.../ocspcache.sqlite3`（及 `DatabaseDomain/MobileIdentityData/*`），正确 flags/owner，报告恢复是否接受（无 205）及黑名单是否临时清除。此为实验，非保证修复。

## 用户纠正：iOS 27 没有 ErrorCode 205

- 用户实测确认 **iOS 27 不会对这些恢复条目返回 205**。之前我把 205 套错上下文（那是 Nugget 的 PosterBoard/AppDomain 那档事）。
- 修正结论：iOS 27 上恢复**协议层未被拒**；失效 = 效果不持久。两点：(a) 目录占位符被重做的 `RestorePostProcess`（MBAtomicBool/ULong）静默忽略，不再“搞乱写入”清空目标文件；(b) 即使清空，trustd 自修复 + 重校验（OCSP/CRLite）立即重建吊销判定。
- 含义：**清除法（v1.0 ConcreteFile 空内容）在 iOS 27 能落地**（无 205 阻挡），唯一剩下 trustd 重校验窗口；而 `ocspcache.sqlite3` 是缓存、不受 `_SecFixTrustdFilePermissions` 管 → 正好是“临时清黑名单”的可行窗口。清除法可行性因此上升。
- 已更新 `iOS27-FAILURE-ANALYSIS.md`（去掉 205 归因，改为“无协议拒绝 + 效果不持久”），并 softening `sparserestore` 里 205 注释。代码修复的 205 重试分支现为无害死分支。
